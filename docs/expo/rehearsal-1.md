## Fix list

### P1: would embarrass us on stage

1. **CD redeploys the live demo during the slot.** Every merge to `main` (the swarm merges every few minutes) runs `cd` → deploy on this laptop. All containers restart and the open page shows **Live connection lost** and **Failed to fetch**. This happened during attempt 1. *Fix:* freeze merges to `main` and disable the deploy job before the expo, for example by adding `if: vars.DEPLOY_FROZEN != 'true'` on the deploy job in `.github/workflows/cd.yml` and setting the repo variable, or by pausing the swarm. Add a line to DEMO.md "30 minutes before": "confirm no `cd` run is queued (`gh run list --workflow cd.yml --limit 3`)".
   - **Routed:** not web (`.github/workflows/cd.yml` and expo-day process). Add `if: vars.DEPLOY_FROZEN != 'true'` to the `deploy` job, set the repo variable before the slot, pause swarm merges, and add the `gh run list --workflow cd.yml --limit 3` check to DEMO.md "30 minutes before".
2. **The stuck-truck alert never appears.** `simulator/src/main/java/io/aetherstream/simulator/Truck.java:62-63` ties the stop to sim minutes 5-20 since *simulator start*, not since pipeline start. *Fix (code):* trigger truck-007's stop relative to the first event after a scenario reset, or let the **Breakdown** scenario pause the selected truck for at least 10 sim minutes, and point DEMO at **Breakdown truck-007**. *Fix (script, if no code change):* restart only the simulator container about 1 minute before the slot, and remove "about 90 s again" after Run or Restore from DEMO.md.
   - **Routed:** not web (simulator + DEMO.md). In `simulator/src/main/java/io/aetherstream/simulator/Truck.java:62-63`, make the **Breakdown** scenario (or a scenario reset) stop the chosen truck for at least 10 sim minutes, starting from when the scenario is applied, not from simulator start. Then point DEMO.md at **Breakdown truck-007**. Until then, DEMO.md should say to restart only the simulator about 1 minute before the slot, and drop "about 90 s again" after Run or Restore.
3. **No Recovered banner after Kill.** In `web/src/app/panels/LivePanels.tsx` (around line 170), `Recovered in …` shows only while `lastExecutionEvent` is `RECOVERED`. The next `CHECKPOINT_COMPLETED` overwrites it within about 1 s, and `RECOVERY_HOLD_MS = 3000` (`web/src/app/state/executionStatus.ts:6`) only holds the *Recovering* state. *Fix:* keep a `recoveredAt` and duration in state, and show `Recovered in X s` (green) for 10 s after RECOVERED, whatever checkpoint events arrive. Add a test next to `recoveryHold.test.tsx`.
   - **Fixed in T158.** The store now records `lastRecovery` when a RECOVERED event arrives, and also when the execution goes from RECOVERING to RUNNING with no RECOVERED event. The banner shows green **Recovered in X s** (or **Recovered from checkpoint #N** when the server sent no duration) for 10 s, whatever checkpoint events follow. Tests: `web/src/app/__tests__/recoveredBanner.test.tsx`. **Root cause, routed (control-api):** `control-api/.../ws/ExecutionEvents.java` only sends RECOVERING/RECOVERED once it has *seen* a worker go missing from `/coord/state`. The most likely cause: the killed worker restarts with the same id before the 1 s poll notices it is gone (the page showed "3 alive" the whole time). The server then sends `REBALANCED` (state RECOVERING) and nothing after it, which matches what the rehearsal saw. Fix there: when the coordinator reports state RECOVERING, treat it as a recovery even if no death was observed (`stateEvent` → `RECOVERING`, then `RECOVERED` on → RUNNING, with `durationMs` measured from the RECOVERING observation).
4. **Queue capacity is 32 on screen, but the hint, DEMO and contract 03 say 1000.** `docker-compose.yml:198,205,212` sets `WORKER_QUEUE_CAPACITY: "32"`. An examiner reading "bounded at 1,000" next to `32/32` will ask. *Fix:* set it back to 1000 (contract 03 §1). If 32 is kept on purpose so backpressure shows quickly, change the hint in `web/src/app/chaos/ChaosPanel.tsx`, DEMO.md and contract 03 together (the contract is the boss's change).
   - **Routed:** not web. Set `WORKER_QUEUE_CAPACITY` back to `"1000"` in `docker-compose.yml:198,205,212` (contract 03 §1). If 32 stays on purpose, contract 03 and DEMO.md must change (boss). Web side, done in T158: the Chaos hint now names the capacity the workers actually report ("bounded at 32" today, "bounded at 1,000" after the compose fix), so it always matches the queue bars.
