# t261119-0314-506b (T86) report

Root cause was in the worker, not the coordinator: `TaskRuntime` set `highestCheckpointRequested` (and `lastCheckpointId`) from `ASSIGN.restoreCheckpointId`. For a savepoint restore that id belongs to the *source* execution (e.g. 3), so the new execution's TRIGGER_CHECKPOINT 1, 2, ... were dropped as "old" and checkpoints never completed. Fix: new `TaskRuntime.checkpointBaseline(assign)` uses the restore id only when the manifest key is under `executions/{thisExecution}/`. A savepoint manifest (`savepoints/...`) counts as 0. `Worker` uses the same helper for its status.
Tests: `TaskRuntimeTest.restoreFromAnotherExecutionsSavepointAcceptsCheckpointsFromOne` fails without the fix and passes with it. `SavepointTest.executionRestoredFromSavepointCompletesItsOwnCheckpointsOneAndTwo` (fake clock, in-memory repo) shows the coordinator side completes checkpoints 1 and 2 after a restore from checkpoint 3. All `:engine:test` tests pass locally. This machine only has JDK 25, so I ran them with a temporary init script outside the repo (toolchain 25, `--release 21`).
`.github/workflows/ci-e2e.yml` has no `E2E_EXTENDED` line on this branch or on origin/main (ef6fefe), and `demo-e2e.sh` already runs steps 1-11 unconditionally, so nothing was changed there. Left: ci-java and ci-e2e still need to go green on the branch CI. Docker was not run on vivek-pc.
