# T29: Full-system demo script on docker compose: run pipeline, kill a worker container, recover, compare (CI workflow)

Lane 7/8 (infra + tests). The whole stack runs with `docker compose up -d --build` (root docker-compose.yml: kafka,
postgres, minio, coordinator, worker-1..3, simulator, control-api on 18080, web on 8088). Write a script that drives the
REAL system through the control-api exactly like the live demo, and a separate CI workflow that runs it.

Files (create only these):
- infra/scripts/demo-e2e.sh (bash, `set -euo pipefail`, uses curl + jq (install jq in CI); base URL env `API`, default
  http://localhost:18080)
- .github/workflows/ci-e2e.yml

demo-e2e.sh steps (print a clear numbered PASS/FAIL line for each; dump useful JSON on failure; exit non-zero on any FAIL):
1. Wait up to 180 s for GET /api/ready status UP.
2. GET /api/pipelines/demo; POST /api/pipelines/validate -> valid true; POST /api/pipelines; POST
   /api/pipelines/{id}/executions with a random idempotencyKey -> state RUNNING.
3. Wait up to 120 s until /api/results/windows returns >= 8 rows (1-minute windows; sim runs 10x so ~6 s each) and
   /api/executions/current lastCompletedCheckpoint >= 2.
4. POST /api/chaos/late-events {count:20, lateByMs:180000}; within 30 s /api/results/dead-letters?kind=LATE has >= 1 row.
5. Note generation G and last checkpoint C; `docker kill aether-worker-2-1` style kill of the container that owns the most
   partitions (find container by the workerId from /api/workers: WORKER_ID env = worker-N; use `docker compose kill worker-N`).
   Within 20 s execution state becomes RECOVERING or generation > G; within 60 s RUNNING with generation > G and
   restoredFromCheckpoint >= C. Print the recovery time.
6. Wait 20 s more, then POST /api/compare (retry on 409 for up to 60 s) -> match true and matched == referenceResults > 0.
   Print "N / N results match".
7. POST /api/chaos/slow-sink {delayMs:200}; within 30 s some worker in /api/workers has backpressured=true; then
   {delayMs:0}; within 60 s none is backpressured.
8. GET /api/version commit equals env EXPECT_SHA when it is set.

ci-e2e.yml: on push to main and task/** (paths-ignore swarm/**, boss/**, docs/**, **/*.md), pull_request, and
workflow_dispatch; per-ref concurrency with cancel-in-progress; ubuntu-latest; timeout 30 min; `GIT_SHA=${{ github.sha }}
docker compose up -d --build`; `EXPECT_SHA=${{ github.sha }} bash infra/scripts/demo-e2e.sh`; always: `docker compose ps`,
`docker compose logs --no-color > compose-logs.txt`, upload it as an artifact, `docker compose down -v`.
Use current action majors (actions/checkout@v5 or newer, actions/upload-artifact@v5 or newer).

Acceptance check: shellcheck-clean script (add a first job `lint` in ci-e2e.yml running shellcheck), and the `e2e` job
runs. The e2e job may fail on your branch only because backend features (worker runtime, compare endpoint) are not on main
yet - say exactly which step failed and why in your result.
