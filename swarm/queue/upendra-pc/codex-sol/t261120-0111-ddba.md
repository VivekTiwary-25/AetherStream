# Recon for the new expo UI (read-only code study, write one report file)

Files: design/ui-glorious/RECON.md (new, the ONLY file you write besides your report). Read anything under web/, api/ (or control-api), simulator/, engine/, scripts/, docs/expo/, docker-compose files, playwright config. Do NOT read or describe swarm/.

We are rebuilding the web UI for an expo demo. Before anyone builds, we need facts. Read the code (do not run the full stack) and write design/ui-glorious/RECON.md in plain English. For every item give: the answer, the exact file paths with line numbers, and the names of endpoints / hooks / message types. About 10 lines per item, no padding. If something does not exist, say "does not exist" plainly.

a) Kill worker: how the old UI's "Kill worker" button kills a worker. Endpoint, method, request body, what the server does (docker kill/stop? process signal? which container names?), and whether the worker restarts by itself (restart policy).
b) web/src/app/editor/: what is there? Is there a usable node canvas (which library)? Could it be reused for a 5-node-type pipeline editor, or is React Flow (@xyflow/react) needed?
c) Can the engine run user-defined pipelines at runtime (submitted while running)? Expected: no.
d) Simulator controls: does it support (1) a truck breakdown / stopped status, (2) start, (3) pause, (4) reset, (5) time speed? For each: exists yes/no, how it is triggered (endpoint/env/CLI). Also "Send late events": how the old UI does it (endpoint, what it sends).
e) For each old panel (speed windows, deliveries/min, alerts, workers, dead letters / failed records, checkpoint timeline, events/s or throughput, engine status): which React hook, REST endpoint or WebSocket message type feeds it, and the data shape (field names).
f) Worker-card bug: in the rehearsal, worker cards did not reliably show a killed worker even while the engine was in recovery. Trace where worker state in the UI comes from (endpoint/WS -> hook -> component), how "dead"/"recovering" is decided, and give your best guess of the cause with file:line. Do not fix it.
g) Simulator truck count: how it is configured (env var, config file, compose), default value, and the exact change to get 6 trucks through config only.
i) Truck event schema: the exact fields of one simulator truck event (name, type, example value), and which of them the API/WebSocket exposes to the UI. Also: how is a truck's partition and its owning worker (W1/W2/W3) known in the API?
j) Web stack facts: framework + version (React/Vite/Next?), router, state/data libs, chart library already used, CSS approach, package manager, dev server command and port, production build/serve (how web is served in docker), Playwright config file and its base URL, how the tests are run, and where DEMO.md and docs/expo/CHEATSHEET.md are.
k) How to run the full stack locally (compose command, ports for web/API/WS), and where the API base URL / WS URL is configured in the web app.

Acceptance: RECON.md exists with sections a-k (there is no h), each with file:line references. Keep it under 400 lines.
