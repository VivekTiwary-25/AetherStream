# Build the new "glorious" UI shell (shared foundation for 4 parallel tracks)

Files: web/src/main.tsx, web/src/glorious/** (new), web/package.json + lockfile, web/public/glorious/** (new), web/vite.config.ts (only if needed), web/nginx or web/Dockerfile config (only for the /pipelines/editor fallback), tests/ui/playwright.config.ts (only the classic base URL / init script). Read design/ui-glorious/design-pack.md, design/ui-glorious/liveworld-mockup.png and home-mockup.png. Section 0, 1 ("Shell") and "HOME" of design/ui-glorious/BOSS_PROMPT.md are your spec; where it disagrees with design-pack.md, BOSS_PROMPT.md wins. Ignore its swarm/boss instructions.

Context: React 19 + Vite 7 + TypeScript web app in web/. The old UI (web/src/App.tsx and web/src/app/**, web/src/city/**) must keep working unchanged. Four other workers will build inside web/src/glorious/{map,analytics,logs,pipelines}/ in parallel right after you, using ONLY the shell API you create. Make that API small, typed and documented.

## Build
1. Entry switch in web/src/main.tsx: `?ui=classic` -> render the existing `<App />` exactly as today (so `?ui=classic&city=classic` keeps working). Otherwise render the new `<GloriousApp />` from web/src/glorious/GloriousApp.tsx. Do NOT edit App.tsx or anything under web/src/app or web/src/city. Old vitest tests render <App/> directly and must still pass.
2. Existing Playwright tests (tests/ui/) must still run against the classic UI: change only playwright.config.ts (e.g. a baseURL/query or an init script) so every old test gets the classic UI. Do not edit the test files. If that is impossible from config alone, say so in the report.
3. web/src/glorious/shell/:
   - tokens.css: CSS variables (glass bg rgba(255,255,255,0.55), strong glass for text-heavy windows ~0.72, blur(20px) saturate(140%), 1px rgba(255,255,255,0.6) inner border, soft wide shadow, radius 20-24px, cream active pill colour from the mockup, text colours meeting WCAG AA on glass, status colours). Neutral, NO blue tint. Font Inter bundled locally via @fontsource/inter (the expo may have no internet; no Google Fonts CDN).
   - GlassSurface (props: strong?: boolean, className, children).
   - GlassWindow: draggable + resizable (react-rnd), title bar with close button and optional back arrow (props: title, onBack?), click/focus brings to front, Escape closes, keyboard accessible (focusable title bar, close button). Changing its children must NOT change its size or position.
   - WindowManager (React context + hook `useWindows()`): `open(id, {title, render, initial?: {x,y,w,h}, strong?})` opens or brings to front if already open; `close(id)`; `isOpen(id)`. New windows open to the right of the sidebar, cascading. Windows float over the current screen (the map stays visible underneath).
   - ClayButton: soft clay-like primary button, min 44x44 px touch target, visible focus ring.
   - Sidebar: ONE glass sidebar on the left. Items: Home, Live World, Analytics, Pipelines, Settings (simple inline SVG icons). On Home it is a minimal icon rail (labels hidden, aria-labels kept). On other screens it shows labels; active item = warm cream pill like liveworld-mockup.png. Clicking Analytics or Settings TRANSFORMS the same sidebar: other items fade out, that section's sub-options fade in, a back arrow restores normal nav. Sub-options come from a registry the tracks fill: export `registerSidebarSection('analytics' | 'settings', items: {id, label, icon?, onSelect}[])` or an equivalent typed config file `web/src/glorious/sections.ts` that each track can append one line to. Pick the simplest that avoids edit conflicts (one file per track is best, e.g. analytics/menu.ts, logs/menu.ts, imported by the shell). Put placeholder items now: Analytics -> Truck Speeds, Deliveries, Alerts, Events Processed, Failed Records; Settings -> Logs & Recovery. Each placeholder opens a GlassWindow saying "Coming soon" (tracks will replace them; this is temporary).
   - StatusPill (top right, on every screen): engine status as TEXT and a colour dot (Running / Degraded / Recovering / Stopped) plus live events/s. Both must come from REAL engine data: find the existing hook/endpoint/WebSocket the old UI uses for engine status and throughput (look in web/src/api and web/src/app/state) and reuse it. Do not invent a status. If the API is unreachable show "Stopped" or "Disconnected" honestly.
   - Router: tiny, no new router library. Screens: home, live, pipelines (and a separate full-page route /pipelines/editor that renders web/src/glorious/pipelines/EditorPage.tsx placeholder WITHOUT the sidebar, because it opens in a new tab). Use history/pathname or hash; make sure a direct load and refresh of /pipelines/editor works in `vite dev`, `vite preview` and the production docker web server (add an SPA fallback there if missing).
   - Motion: Home -> Live World = the map screen slides up from the bottom like an Android app drawer (~500 ms ease-out); sidebar transform = fades; window open/close = short fade/scale. `prefers-reduced-motion`: fades only, no slide, no video autoplay.
4. web/src/glorious/home/: full-screen muted autoplay loop playsinline <video> from web/public/glorious/home-loop.mp4 with poster web/public/glorious/home-poster.jpg, object-fit: cover (copy both files from design/ui-glorious/). Reduced motion: poster only. Sidebar rail + StatusPill are real HTML on top; nothing painted. A clear "Live World" entry (the sidebar item, plus optionally a ClayButton) triggers the slide-up.
5. Stub folders, one placeholder component each, so tracks have a home: web/src/glorious/map/LiveWorld.tsx (glass card "Map loads here"), analytics/, logs/, pipelines/ (PipelinesPanel.tsx + EditorPage.tsx). Add web/src/glorious/README.md (<= 60 lines) documenting the shell API: how a track opens a window, adds sidebar sub-items, reads status, and the rule "each track edits only its own folder".
6. Accessibility: keyboard path to everything, visible focus rings, status as text + colour, aria labels.

## Rules
- Only real data. No mock data, no fake numbers, no fake controls. `npm run check:no-mock` must still pass on the build.
- Do not touch engine, simulator, control-api or old UI code.

## Check before you finish
In web/: `npm ci` (or install), `npm run lint`, `npm test`, `npm run build`, `npm run check:no-mock`. All must pass. Then run `npx vite preview` (or dev) briefly in the background and load / , /?ui=classic and /pipelines/editor once (curl is fine) to confirm they serve; stop the server afterwards. Report: the shell API in 5 lines, which hook feeds the StatusPill, and the result of each command.
